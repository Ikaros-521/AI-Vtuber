# AI-Vtuber WebUI 重设计方案

> 版本：v1（2026-10）· 角色：产品经理视角的信息架构与交互重设计
> 配套可交互原型：`docs/redesign/prototype.html`（浏览器直接打开）

---

## 0. 一句话结论

现状的问题不是「不好看」，是**把 651 个配置字段按 config.json 的结构平铺给了所有用户**。本方案把界面从「配置文件编辑器」重构为「开播工作台」：用户看到的第一屏是*我要开播还差哪一步*，而不是*这里有 137 张表单卡片*。

---

## 1. 现状盘点（全部来自代码实证）

| 维度 | 数据 |
|---|---|
| 顶级工作区 | 9 个（总览/聊天/直播接入/人设与大脑/声音与表现/弹幕与礼仪/互动与玩法/外设与联动/运维与系统） |
| 配置字段总数 | **651**（voice 224 · brain 158 · interaction 100 · hardware 52 · danmu 48 · live 36 · system 33） |
| LLM 提供商卡片 | 10 家全量平铺（ChatGPT 兼容/智谱/Gemini/通义/千帆/langchain/AnythingLLM/Dify/火山/自定义） |
| TTS 提供商卡片 | 13 家全量平铺（edge-tts/VITS/bert_vits2/GPT-SoVITS/azure/cosyvoice/…） |
| 平台入口 | 12 个（含 5 个已并入「弹幕监听助手」的遗留项） |
| 形象驱动 | 7 种 |
| 可选玩法/功能模块 | 20+（点歌/积分/绘图/闲时/定时/文案/按键联动/串口/翻译/搜索/识别/…） |
| 队列优先级 | 20 个数字输入框手动编号 |

### 1.1 用户反馈翻译成设计问题

用户说「不好用、难理解、不知道怎么配置」，落到代码上对应六个结构性问题：

1. **N 选 1 被做成了 N 全填**。运行时 `chat_type` / `audio_synthesis_type` / `visual_body` 各只有一个生效值，但 UI 把全部 10 家 LLM、13 家 TTS 的表单一视同仁平铺。用户的真实任务是「选 1 家 + 填 3~5 个必填框」，界面上看到的却是上百个框。已有的「板块显示/隐藏」藏在上千像素外的系统页最底部，且和「当前选了谁」毫无联动——用户无法建立「选中 ⇒ 只看选中」的心智。
2. **信息架构是文件的镜像，不是任务的镜像**。页面切分对应 v2 的 Python 模块（llm.py / tts.py / talk.py…），而用户脑子里的任务是：*接直播间 → 给脑子 → 配嗓子 → 配脸 → 开播*。总览页的「开播四件套」已经摸到了正确答案，但它只是一页 checklist，没有贯穿产品。
3. **必填与专家参数同权**。API 密钥（不填不能用）和 `presence_penalty`（99% 用户永远不碰）出现在同一行网格里，一行 7 个数字框是常态。小白无法判断「我到底要填几个」。
4. **关键风险埋在 placeholder 里**。B 站 cookie 要 F12 抓包、有封号风险、建议小号——这些一句话就能劝退或救命的提示写在输入框占位符里，滚动即失。
5. **排序任务被做成了编号任务**。20 个模块的播报优先级让用户手动填数字。它是排序，就该拖拽。
6. **保存/运行模型不可见**。改完的草稿要点右下角折叠坞里的「保存配置」；「保存了配置 ⇒ 需要重跑程序才生效」这条因果链只存在于 tooltip。

## 2. 设计原则（六条，按优先级）

1. **管道心智**：产品本质是一条信号链——*弹幕从哪来 → 谁想 → 谁说 → 长什么样 → 怎么播*。整个 IA 围绕这条链组织，首页把它画出来。
2. **选中即所见（Pick-one）**：所有 N 选 1 的能力改为「选卡墙 + 只渲染选中者的表单」。备选服务商永远只是一张带一句话简介和标签（免费/需 API Key/需本地部署）的小卡。
3. **渐进披露**：每个表单两层——必填区（≤6 个框）+「高级参数」折叠区（默认收起；全局「专家模式」开关可一次性展开）。
4. **玩法即开关**：20+ 可选功能不进主导航、不占默认视野，收进「玩法库」开关卡片；开启才展开配置。
5. **就地验证**：凡是「连服务」的配置旁边就有「测试」（LLM 连通、TTS 试听、模型列表、串口自检）。配置好的定义从「填过了」变成「测过了」。
6. **危险显性化**：封号风险、模板覆盖、重启丢改动，用统一的警示条组件钉在卡片顶部，永不写进 placeholder。

## 3. 新信息架构

### 3.1 导航：9 → 5

| 新导航 | 承接的旧工作区 | 一句话定位 |
|---|---|---|
| **开播台** | 总览 + 聊天（测试入口） | 现在能开播吗？差哪一步？ |
| **基础设置** | 直播接入 + 人设与大脑 + 声音与表现（连接部分） | 四步配齐信号链：直播间 → AI 大脑 → 声音 → 形象 |
| **玩法库** | 互动与玩法 + 外设与联动 + 翻译/搜索/识别 | 20+ 可选玩法，开关式启用 |
| **弹幕管家** | 弹幕与礼仪 | 什么弹幕进、怎么答谢、谁先播 |
| **系统** | 运维与系统 | 数据/日志/备份/账号/外观/模块开关 |

全局层保留：顶栏常驻「运行状态 + 开始/停止」「保存 + 未保存数」「Ctrl+K 搜索」。聊天测试页保留为开播台内嵌面板 + 可弹大窗（不再是主导航项）。

### 3.2 基础设置的四步结构

二级导航做成**步骤条**而非普通页签，直接呼应「四步开播」：

- **① 直播间**：平台选卡墙（12 入口，含「不接平台先试聊天」）→ 选中平台的认证表单（扫码/cookie/开放平台，B 站 cookie 顶部钉警示条）。
- **② AI 大脑**：LLM 选卡墙（10 家，标注 免费·需Key·本地部署）→ 选中者表单（密钥/模型 + 「测试对话」）→ 页内次级页签：「记忆与模板」（上下文长度、前后缀提示词、回复语言）/「快捷问答」（原本地问答）。
- **③ 声音**：三个页签——**说话（TTS）** / **听话（语音对话 STT + 打断 + 唤醒）** / **变声（SVC）**。TTS 是 13 家选卡墙 + 必填/高级两层 + 「试听」。播放策略（间隔/切分）收进「高级」。
- **④ 形象**：7 种驱动选卡墙（Live2D 默认推荐位）+ 端口/模型名 + 预览链接。

### 3.3 关键页规格

**开播台**
- 顶区：运行状态大按钮组（开始直播 / 停止 / 运行日志）。
- **信号链可视化**：横向 4 节点卡（直播间→AI 大脑→声音→形象），每节点显示当前选中的服务名 + 三态灯（✓ 已配置且测试通过 / ● 已配置未测 / ○ 未配置），点击节点直达对应设置页。
- **下一步建议**：基于就绪度只给一条最重要的动作（「还差 1 步：声音还没配置 → 去配置」），不给清单墙。
- 次区：聊天测试（验证大脑+声音的端到端通路）、已启用玩法概览。

**玩法库**
- 三组卡片网格：**直播互动**（点歌/积分/AI 绘图/答谢）、**自动运营**（闲时暖场/定时任务/文案轮播/动态文案）、**进阶联动**（按键联动/串口硬件/自定义命令/弹幕助手/联网搜索/双语翻译/画面识别/人数自适应）。
- 每卡：名称 + 一句话 + 主开关；开启后卡片原地展开核心字段，「详细配置」进抽屉。过滤器「已启用 N」。
- 与弹幕管家的边界：答谢的**文案编辑**归弹幕管家，答谢**玩法开关**在玩法库只留一个入口链接，避免两处重复编辑（用户明确反感导航/内容重复）。

**弹幕管家**
- 页签：**触发规则**（前后缀、LLM 触发词）/ **过滤屏蔽**（违禁词/黑名单/表情/长度，危险词库路径收进高级）/ **答谢文案**（入场/礼物/关注三个文案编辑器，支持变量提示 `{username}`）/ **播报顺序**。
- **播报顺序 = 拖拽排序**，替代 20 个优先级数字框；「高级」里保留消息队列长度等容量参数。
- 「周期性触发」四件套（周期 min/max + 次数 min/max）合并为一个**频率复合控件**：「每 [5–10] 分钟 · 每次播 [0–1] 条」。

**系统**
- 数据分析（原样保留）/ 日志与数据库 / 配置备份（模板存取，覆盖操作二次确认）/ 账号 / 外观主题 / **模块开关**（原「板块显示/隐藏」，改名并加说明：关掉=从界面移出，不影响已保存配置）。

### 3.4 首次向导

检测 config 为默认/空时自动进入；也可从开播台「重新运行向导」唤起。5 步：平台 → 大脑 → 声音 → 形象 → 完成（一键试运行）。每步只问必填项，高级参数全部走默认；B 站扫码登录在此处做成首选路径（cookie 作为「高级方式」折叠）。

## 4. 全局交互规范

| 规范 | 内容 |
|---|---|
| 保存模型 | 顶栏常驻「保存 (N)」；保存前弹配置摘要确认（沿用 v2/v3 行为）；运行中的程序收到「配置已变更，重启生效」的引导条 |
| 测试反馈 | 所有测试按钮三态：检测中（禁用+动画）→ 成功（绿，显示延迟/模型名）→ 失败（红，显示错误首行） |
| 空态引导 | 未选服务商时表单区显示该能力的「一分钟解释」+ 推荐默认（如 TTS 默认推荐 edge-tts：免费、无需 Key） |
| 字段规范 | 标签人话（「说话嗓音」不是 `voice_name`）；获取路径类提示（cookie 怎么抓、Key 去哪申请）做成「怎么看？」弹出层而非 placeholder；单位进标签（「间隔（秒）」） |
| 危险操作 | 覆盖模板、停播、重启一律二次确认 + 说明后果；封号风险类警示条常驻卡片顶 |
| 键盘 | Ctrl+K 全局搜索保留；表单内 Tab 顺序按必填→高级排列 |

## 5. 迁移策略（不推倒重来）

React 端的 schema 驱动架构（`Field/Section/Workspace` + `configStore`）**全部保留**，改的是呈现层：

1. **第一步（纯前端，零后端改动）**：
   - `AppShell` 顶栏 9 芯片 → 左侧栏 5 项；
   - `WorkspacePage` 外面套「选卡墙」：读 `chat_type`/`audio_synthesis_type`/`visual_body`/`platform` 的当前值决定只渲染哪个 section，其余同级 section 变成选卡；
   - Field schema 增加 `tier: 'required' | 'advanced'` 标记（默认 advanced，逐卡补标 required），渲染层据此分两层。
2. **第二步**：优先级拖拽排序（20 个数字框 → 写回 `filter.priority_mapping`，数据结构不变）；周期四件套复合控件。
3. **第三步**：向导 + 信号链可视化（读现有 readiness 逻辑扩展为三态）。
4. **兼容**：`?tab=` 深链映射到新导航；搜索索引/未保存清单/跳转闪烁机制原样生效。

## 6. 度量

- 首次配置完成时间（向导开始→试运行成功）：目标 ≤ 10 分钟（现状无向导，无基线，上线后建基线）
- 「不知道配哪个」类反馈占比
- 每提供商表单的必填完成率 / 测试按钮使用率
- 高级参数区展开率（验证渐进披露是否真的减少了认知负担）
